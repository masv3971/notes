Handout appendix A, SD-JWT VCExtra · optional, not in the timetable

+SD-JWT VC: how it works

The signed credential
// simplified { "iss": "https://issuer.example-university.se", "vct": "…/credentials/degree", "cnf": { the wallet's public key }, "_sd": [ hash(degree) ], "address": { "country": "SE", ← visible to everyone "_sd": [ hash(street_name) ] }, "_sd_alg": "sha-256" }
Travels to the wallet too
["3b9d…salt", "degree",
 "Master of Science…"]SHA-256 of this gives hash(degree)
["c04e…salt", "street_name",
 "Drottninggatan"]SHA-256 of this gives hash(street_name)
The salt stops anyone from guessing the value.
When presenting, the verifier only needs the degree
signed JWT~degree disclosure~key binding proof (KB-JWT)
street_name never leaves the phone. The country is still visible.
TakeawayThe credential is signed once. The wallet chooses what to show, and the verifier recomputes the hashes.

SD-JWT VC is a JWT (signed JSON) with selective disclosure and a credential type.

Each hidden attribute becomes a small package: salt, name, value. Only the package's hash sits in the signed part.

The verifier hashes each package it receives and looks for the hash in _sd.

Limit: linkability. The same signature is visible to every verifier.

+Token Status List: how revocation works

The credential points to a place in a list
// simplified { "iss": "https://issuer.example-university.se", "status": { "status_list": { "idx": 4711, "uri": "…/statuslists/1" } } }

1 bit per entry: 0 = valid, 1 = revoked. Suspended (value 2) needs 2 bits. Blue frame: our credential, idx 4711.
SUNET/vc: every list starts with 1,000,000 random decoy entries. A new credential takes a random free slot, and other decoys change at random in the same step. You hide among a million. It uses 8 bits per entry.
The verifier
fetches the signed list→reads the bit at idx 4711→0: valid. 1: reject.
The copy is kept until its ttl. A new revocation can take that long to arrive.
TakeawayThe verifier downloads the whole list, so the issuer cannot tell which credential was checked. The cost is delay.

The verifier never calls the issuer. Revocation works because the issuer publishes a signed list that anyone can download.

Each credential gets a position in the list when it is issued. The credential carries the address of the list and the position.

To revoke, the issuer flips the bit and publishes a new signed list. Verifiers see it when their cached copy expires.

Privacy: the verifier fetches the whole list, so the issuer cannot tell which credential was checked. It can still see the verifier's address and timing.

SUNET/vc creates every list with a million decoy entries holding random values. A real credential takes a random free decoy slot. In the same step up to ten decoys get new random values, so changes happen at random places. A new list is created when 1,000 decoys or fewer remain. This is herd privacy from the first credential. The lists use 8 bits per entry, and our reading code ignores the bits field. Read from the repository code, not reviewed by the team.

"Who runs the list, and what does a verifier do when it is down?"

The draft defines three values: 0 valid, 1 invalid (revoked), 2 suspended. Suspended needs 2 bits per entry. Values and field names checked against draft-ietf-oauth-status-list-21.

9Two ways to get a credential

Authorization code flow
Pre-authorized code flow
Who is the person?
During the flow. The person logs in and consents at the issuer.
Before the flow. The issuer already checked them: an office, a form, a letter.
How it starts
An offer from the issuer, or the wallet on its own
Always an offer with a one-time code, as a QR code or link
Token request
Authorization code
Pre-authorized code, plus a PIN if the issuer wants one
Then
Same for both: access token, credential request with proof of key, credential
Good to know
Required by HAIP. More moving parts: redirects, login, consent.
Not required by HAIP. A copied code is enough, so: short life, single use, PIN.
TakeawayThe only difference is when the issuer learns who the person is.

Both flows end the same way. They differ in one thing: when the issuer finds out who the person is.

Code flow: the person logs in during the flow. Example: click "request your diploma" on the university site, the wallet opens, log in at the university.

Pre-authorized flow: the issuer checked the person before. Example: checked at an office, then a QR code by letter or email and a PIN by text message.

Nobody signs the offer, so the wallet must check the issuer as if it had started the flow. A fake issuer can also phish a PIN meant for another service.

"How does the issuer know who the person is today: a login, or a decision in a back office?"

SUNET/vc supports both. The next slide walks through the code flow.

Handout section 13Slide 14 · 4 min

14Working in the field

Questions that show you understand

• Which role are we playing: issuer, verifier, or both?

• Who is the trust anchor, and who decided that?

• Is that in the final spec, or still a draft?

• What happens when a credential is revoked? Who runs the list?

• Has this been tested with someone else's wallet?

Red flags

• "It's standard", without saying which one or which version.

• A draft described as stable.

• No named owner for who may become an issuer.

• A demo that works only with its own wallet.

AskWhich red flag have you already seen?

Ask which version, which status, and who owns the trust decision.

The hard risks are rarely the cryptography: moving standards, interoperability, governance, and dependencies between EU projects and national decisions.
